Незнакомые термины — в [словарике](../adr/glossary.md), сноски [[N]] ведут туда.
Связанные документы: [план](../plans/laravel-port.md), [ADR-0001…0006](../adr/README.md), [контракт API](../api.md), [статус](../STATUS.md)

## Проблема

HotelPulse написан на .NET. Нужна вторая реализация бэкенда на PHP/Laravel с тем же поведением. Она должна быть пригодна для продакшена уровня B2B SaaS, а не только для демо.

Ориентир по масштабу — HURMA System (HR SaaS, 1000+ компаний-клиентов, десятки тысяч пользователей, среди клиентов банки и госорганы). Требования ниже **все обязательные**, порядок не означает приоритет. Самое частое у такого продукта — не рекордный трафик, а **всплески одновременных запросов** (утро понедельника, массовые операции, повторы из-за плохой сети). Как раз они в аудите .NET ломали данные (ADR-0003…0005), поэтому пункты 1 и 6 так же важны, как надёжность и защита данных:
1. **Корректность при одновременных запросах.** Данные не портятся ни при каком порядке запросов.
2. **Надёжность фоновой обработки.** Сообщения не теряются, повторы безопасны.
3. **Защита данных.** Персональные данные не попадают в логи, секреты не попадают в репозиторий.
4. **Наблюдаемость.** По логам видно, что произошло с запросом и с сообщением.
5. **Горизонтальное масштабирование** [[49]](../adr/glossary.md#t49)**.** Веб и worker можно запустить в N копиях, и ничего не сломается.
6. **Предсказуемость под нагрузкой.** При одновременных запросах — ни одного `500`, ни одной взаимоблокировки, которая дошла бы до клиента. Время ответа измеряется и не деградирует скачком (см. «Нагрузочная проверка»).

## Цель

`apps/api-laravel` отвечает **байт-в-байт по тому же контракту** (`docs/api.md`), что и .NET API: те же маршруты, коды, JSON-поля, заголовки, сообщения в очереди. Фронтенд работает с любым из двух бэкендов без изменений. Все правила из ADR-0001…0005 выполняются.

## Вне рамок

- Аутентификация и мультитенантность. В .NET их тоже нет. В разделе «Путь к продакшену» записано, как их добавить.
- Перенос данных между .NET- и Laravel-базами. Базы раздельные и независимые.
- Замена RabbitMQ или Redis другими сервисами.

## Архитектура

```
apps/api-laravel/
  app/Domain/            правила без I/O (аналог HotelPulse.Domain): enum'ы, final-классы со static-методами
  app/Infrastructure/    Postgres-репозитории (сырой SQL), Redis-кэш, RabbitMQ publisher/consumer
  app/Http/              контроллеры, FormRequest-валидация, middleware
  app/Console/Commands/  hotelpulse:relay, hotelpulse:consume
  database/migrations/   SQL 001–003 дословно через DB::unprepared
  tests/Unit, tests/Feature (Pest)
  docker/                Dockerfile, supervisord.conf
```

Процессы:
| Процесс | Команда | Масштабирование |
|---|---|---|
| web | `php artisan octane:frankenphp --port=$PORT` | N копий, состояния нет |
| relay | `php artisan hotelpulse:relay` | N копий безопасны (`FOR UPDATE SKIP LOCKED`) |
| consumer | `php artisan hotelpulse:consume` | N копий, prefetch=1 |

На Render free все три работают в одном контейнере под `supervisord`. В продакшене это отдельные процессы или контейнеры.

## Правила (переносятся из .NET один в один)

1. **Двойное бронирование** запрещает exclusion constraint [[5]](../adr/glossary.md#t5) `bookings_no_overlapping_stay`. `QueryException` с SQLSTATE `23P01` → 409.
2. **Смена статуса — только compare-and-set:** `UPDATE ... WHERE id = ? AND status = 'pending'` с проверкой числа изменённых строк или `UPDATE ... RETURNING`. **Запрещено:** `$model->status = ...; $model->save()` после чтения. Eloquent-модели [[36]](../adr/glossary.md#t36) используются только для чтения.
3. **Создание бронирования** — одна транзакция:
   - `pg_advisory_xact_lock(hashtextextended(hotel/room, 0))` (ADR-0005);
   - проверка повтора по Idempotency-Key;
   - вставка в `bookings`, `outbox`, `idempotency_keys`.
4. **Ошибки при создании:**
   - `23P01` при наличии ключа → сначала повтор по ключу, потом 409 (ADR-0004);
   - `23505` на `idempotency_keys_pkey` → повтор;
   - `40P01` → повтор транзакции до 3 раз.
5. **Отмена** — read → decide → CAS [[17]](../adr/glossary.md#t17), до двух попыток. Событие отмены дописывается в `events` внутри UPDATE (ADR-0003).
6. **Только `pending` и `confirmed` держат комнату.** Constraint, `bookings_availability_idx` и SQL доступности фильтруют одно и то же множество статусов.
7. **Каждая запись, меняющая доступность** (создание, отмена, подтверждение или отказ worker'ом), вызывает инвалидацию кэша отеля.
8. **Сбой Redis не роняет запрос.** Каждая операция с кэшем — в try/catch с таймаутом подключения 250 мс. При ошибке `X-Cache: BYPASS` и чтение из Postgres.
9. **Outbox relay:**
   - строки берутся через `FOR UPDATE SKIP LOCKED LIMIT 20`;
   - публикация с publisher confirms (`confirm_select` + `wait_for_pending_acks_returns`) и `mandatory`;
   - `published_at` ставится только после ack (ADR-0002).
10. **Consumer** идемпотентен: если бронирование уже в терминальном статусе, ack и пропуск. Политика доставки та же, что в `DeliveryPolicy.cs`:
    - poison payload [[41]](../adr/glossary.md#t41) → отбросить;
    - временная ошибка → requeue один раз, потом `rejected`;
    - недоступность БД → requeue всегда.

## API (контракт = `docs/api.md`)

Каждая строка таблицы — feature-тест.

| Случай | Ответ |
|---|---|
| `GET /health`, Postgres отвечает | `200 {status:"ok", version, time}` |
| `GET /health`, Postgres недоступен | `503 {status:"unavailable", ...}` |
| `GET /api/hotels` | `200`, `X-Cache: MISS` при первом запросе, `HIT` при втором, `BYPASS` без Redis |
| `GET /api/hotels/{id}` неизвестный | `404 {error:"Hotel not found."}` |
| `GET .../availability` без дат или с кривыми датами | `400 {errors:[{field,message}]}` |
| `GET .../availability` корректный | `200 {hotelId, checkIn, checkOut, rooms[{..., available}]}` |
| `POST /api/bookings` корректный | `202 {id, status:"pending"}`, заголовок `Location` |
| `POST` с невалидным телом | `400 {errors:[...]}` |
| `POST` с неизвестным отелем или комнатой | `404` |
| `POST` на занятые даты | `409 {error:"Those dates are already held for this room."}` |
| `POST` повтор с тем же ключом и телом | `202` с исходным `id` |
| `POST` с тем же ключом и другим телом | `409` |
| `POST` с `Idempotency-Key` длиннее 200 символов | `400` |
| `POST` 10 параллельно на одну комнату и даты | ровно один `202`, девять `409`, ни одного `500` |
| `POST` 10 параллельно с одним ключом | десять `202` с одним `id` |
| `GET /api/bookings` | `200`, последние 20, новые первыми |
| `GET /api/bookings?ids=a,b` | `200`, в порядке запроса, не больше 20 |
| `GET /api/bookings/{id}` неизвестный | `404` |
| `POST /api/bookings/{id}/cancel` — 5 случаев из `docs/specs/booking-cancellation.md` | `200` / `200` / `404` / `409` / `409` |
| Отмена параллельно с worker'ом | всегда итог `cancelled`, комната свободна, таймлайн полный |
| Worker: бронирование доходит до терминального статуса | `confirmed` с кодом `HP-XXXXXX` или `rejected` |
| Worker: повторная доставка завершённого бронирования | ack, данные не меняются |
| Relay: брокер недоступен | строка остаётся неопубликованной и уходит после восстановления |

## Данные

- Миграции `001_init.sql`, `002_seed.sql`, `003_cancellation.sql` переносятся **дословно**. Схема у обеих реализаций одна.
- Laravel ведёт свою таблицу `migrations` (вместо `schema_migrations` в .NET). Базы раздельные, конфликта нет.
- Миграции запускаются командой `php artisan migrate --force --isolated` до старта web (`--isolated` не даёт двум копиям мигрировать одновременно).
- Для миграций используется **прямое** подключение к Neon (`DATABASE_URL_UNPOOLED`), для работы — пул (`DATABASE_URL`). Через PgBouncer в transaction mode [[37]](../adr/glossary.md#t37) работают транзакционные advisory lock'и [[10]](../adr/glossary.md#t10) (`_xact_`), сессионные — нет. Поэтому используем только `_xact_`.

## Изоляция от .NET-стека

| Ресурс | .NET | Laravel |
|---|---|---|
| Postgres | ветка Neon `production` | отдельная ветка `laravel` |
| RabbitMQ | exchange `hotelpulse`, queue `bookings.created` | exchange `hotelpulse.laravel`, queue `bookings.created.laravel` (настраивается через env) |
| Redis | ключи без префикса | префикс `laravel:` |

## Кэш

Те же ключи и TTL, что в `CacheKeys.cs` и `HotelCatalog.cs`. Инвалидация удаляет ключи отеля и его доступности. Заголовок `X-Cache: HIT | MISS | BYPASS`.

## Требования для продакшена

**Наблюдаемость**
- Логи в stdout в JSON (Monolog `JsonFormatter`), по строке на событие.
- `X-Request-Id` [[43]](../adr/glossary.md#t43): берётся из запроса или генерируется, возвращается в ответе, пишется в каждую строку лога. Consumer пишет `bookingId` и `deliveryTag`.
- Имя гостя и тело запроса **не логируются** (персональные данные [[44]](../adr/glossary.md#t44)).
- `/health` — readiness [[38]](../adr/glossary.md#t38) (Postgres). `/health/live` — liveness (процесс жив, без зависимостей).

**Надёжность**
- Таймауты [[42]](../adr/glossary.md#t42): Postgres `statement_timeout = 5s`, подключение к Redis 250 мс, к RabbitMQ 5 с.
- Consumer и relay обрабатывают SIGTERM [[39]](../adr/glossary.md#t39): заканчивают текущее сообщение или пачку и выходят. supervisord перезапускает упавший процесс.
- Переподключение к RabbitMQ и Postgres с паузой, без падения процесса.
- Octane: worker перезапускается после `--max-requests=1000` (защита от утечек памяти).

**Безопасность**
- `APP_DEBUG=false` [[47]](../adr/glossary.md#t47) в продакшене: трассировки стека не уходят клиенту, ошибка 500 возвращает `{error:"Internal server error."}`.
- Секреты (`APP_KEY`, URL баз) только из env. `.env` в `.gitignore`.
- CORS [[46]](../adr/glossary.md#t46) — только origin'ы из `CORS_ORIGINS`.
- Rate limit [[45]](../adr/glossary.md#t45) на `POST /api/bookings`: 30 в минуту с одного IP. Лимитер хранит счётчики в Redis и **пропускает запрос**, если Redis недоступен (правило 8 важнее лимита).
- Заголовки безопасности: `X-Content-Type-Options: nosniff`, `Referrer-Policy: no-referrer`.
- Docker-образ запускается не от root.

**Нагрузочная проверка**
- Параллельные feature-тесты из таблицы API (10 одновременных запросов) входят в обязательный CI и прогоняются **3 раза подряд**: гонки проявляются не в каждом запуске, в .NET deadlock ловился примерно в каждом третьем.
- Нагрузочный smoke-тест [[55]](../adr/glossary.md#t55) (k6, вручную и перед релизом) против локального `docker compose` для **обеих** реализаций:
  - 50 виртуальных пользователей, 60 секунд, смесь из 80% чтений каталога и доступности и 20% бронирований, часть которых идёт в одни и те же комнаты;
  - критерии: 0% ответов `5xx`, все `409` — только на реально занятые даты, p95 чтений < 200 мс, p95 `POST /api/bookings` < 500 мс;
  - после теста в базе нет пересекающихся активных бронирований и нет бронирований, зависших в `pending`.
- Результаты записываются в `docs/benchmarks.md` (дата, версия, железо, цифры). Если на фронте будут замеры, это их источник.

**Качество (CI)**
- `pint --test`, `phpstan analyse` (уровень 8), `composer audit`, `pest` (unit + feature против настоящих Postgres, Redis и RabbitMQ как сервисов GitHub Actions).
- Job PHP идёт рядом с .NET-job. Изменение не готово, пока зелёные оба.

## Правила кода (Octane-safe)

- Никакого состояния запроса в `static`-полях и синглтонах [[40]](../adr/glossary.md#t40). Синглтоны разрешены только для клиентов подключений: пул PDO, Redis, AMQP-канал.
- `final readonly class` для данных, `enum` для статусов, `declare(strict_types=1)` во всех файлах [[53]](../adr/glossary.md#t53).
- SQL: явные списки колонок, snake_case, полуоткрытые диапазоны `[check_in, check_out)`.
- Названия тестов описывают поведение: `it('keeps worker steps when a cancel races the worker')`.

## Путь к продакшену (не делаем сейчас, но архитектура не мешает)

- **Аутентификация:** Laravel Sanctum [[51]](../adr/glossary.md#t51) (токены) и политики доступа к бронированиям.
- **Мультитенантность** [[50]](../adr/glossary.md#t50) (как у HURMA: много компаний в одной системе): колонка `tenant_id` во всех таблицах и в constraint'ах, Row Level Security в Postgres как вторая линия защиты.
- **Метрики:** OpenTelemetry [[52]](../adr/glossary.md#t52) (время запросов, длина очереди, возраст самой старой неопубликованной строки outbox).
- **Сторож зависших бронирований:** периодическая задача находит бронирования в `pending` старше N минут и переопубликует их.
- **Очистка:** удаление старых опубликованных строк outbox и устаревших idempotency-ключей.
