# Нагрузочная проверка

Сценарий и пороги — из [спеки порта](specs/laravel-port.md) («Нагрузочная проверка»). Скрипты лежат в [`scripts/load/`](../scripts/load/). Термины: нагрузочный тест, k6, p95 — [[55]](adr/glossary.md#t55).

## Как запустить

API запускается с `HOTELPULSE_BOOKING_RATE_LIMIT=0`, потому что все виртуальные пользователи k6 приходят с одного IP. У лимита свои тесты.

```bash
scripts/load/run.sh http://localhost:8080 "postgres://hotelpulse:hotelpulse@localhost:5432/hotelpulse" dotnet
scripts/load/run.sh http://localhost:8081 "postgres://hotelpulse:hotelpulse@localhost:5433/hotelpulse_laravel" laravel
```

`run.sh` запускает k6 (`grafana/k6:2.3.0`) и ждёт, пока worker разберёт очередь. Потом проверяет базу (`after-run.sql`): нет ли пересекающихся активных бронирований и не осталось ли бронирований в `pending`. Переменные `VUS`, `DURATION`, `WINDOW_DAYS`, `ROOMS`, `FIRST_DAY` меняют сценарий.

## Сценарий

- 50 виртуальных пользователей, 60 секунд, без пауз между запросами.
- Около 80% запросов — чтения: список отелей, карточка отеля, доступность на два дня. Около 20% — бронирования на 1–3 ночи.
- Два режима бронирований:
  - **обычный** — окно 365 дней на все комнаты: много успешных вставок и часть конфликтов;
  - **«горячие» комнаты** — окно 14 дней на две комнаты каждого отеля: почти каждое бронирование — конфликт.

## Пороги

| Порог | Значение |
|---|---|
| Ответы 5xx | 0 |
| Коды, кроме 200, 202 и 409 | 0 |
| p95 чтений | < 200 мс |
| p95 бронирований | < 500 мс |
| После прогона: пересекающиеся активные бронирования | 0 |
| После прогона: бронирования в `pending` | 0 |

## Результаты — 2026-11-03, версия 1.1.0

Стенд: одна виртуальная машина, 4 ядра, 15 ГБ. Postgres 18, Redis 8 и RabbitMQ 4 в Docker на той же машине. k6 работает там же.
- .NET: API и worker — отдельные процессы, Release-сборка.
- Laravel: образ в режиме `all` — Octane (4 воркера), relay и worker в одном контейнере.

Реализации запускались по очереди, не одновременно. Паузы демо-конвейера выключены (`HOTELPULSE_STEP_DELAY_MS=0`), уровень логов — warning.

| | .NET, обычный | Laravel, обычный | .NET, «горячие» | Laravel, «горячие» |
|---|---|---|---|---|
| Запросов в секунду | 1 477 | 482 | 3 147 | 631 |
| p95 / p99 чтений | 62 / 81 мс | 131 / 147 мс | 26 / 47 мс | 165 / 200 мс |
| p95 / p99 бронирований | 88 / 117 мс | 136 / 152 мс | 76 / 103 мс | 147 / 180 мс |
| Создано / конфликтов (409) | 3 815 / 14 055 | 2 628 / 3 084 | 124 / 37 644 | 124 / 7 481 |
| 5xx, лишние коды | 0, 0 | 0, 0 | 0, 0 | 0, 0 |
| Пересечения, зависшие `pending` | 0, 0 | 0, 0 | 0, 0 | 0, 0 |
| Все пороги | ✅ | ✅ | ✅ | ✅ |

## Что из этого следует

- **Корректность под нагрузкой подтверждена в обеих реализациях.** Десятки тысяч одновременных попыток забронировать одни и те же комнаты, и при этом ни одной ошибки 5xx, ни одного двойного бронирования, ни одного зависшего бронирования. Это проверка ADR-0001, ADR-0005 и ADR-0009 в условиях, близких к всплеску.
- **В режиме «горячих» комнат обе реализации создали ровно по 124 бронирования.** Ровно столько бронирований на 1–3 ночи помещается в этот набор комнат и дат. Обе дошли до одного и того же предела: ни одной лишней продажи и ни одного потерянного допустимого бронирования.
- **.NET здесь примерно в 3 раза быстрее по пропускной способности, но обе реализации укладываются в пороги с запасом.** Laravel в «горячем» режиме ближе всего к порогу чтений: p95 — 165 мс при пороге 200 мс.
- **Почему обычный режим медленнее «горячего».** Каждое успешное бронирование сбрасывает кэш отеля (ADR-0008), поэтому больше чтений идёт мимо кэша в Postgres. В «горячем» режиме почти всё — конфликты, кэш почти не сбрасывается, и чтения быстрые.

## Чего эти цифры не значат

- **Это не обещание производительности в продакшене.** Всё работает на одной машине, и k6 делит процессор с API, базой и брокером. Цифры годятся для сравнения версий между собой и для поиска регрессий.
- **Сравнение .NET и Laravel не совсем равное.** Laravel-контейнер держит веб, relay и worker в одних и тех же ресурсах. Настройки ни одной из реализаций под нагрузку не подбирались: число воркеров Octane, пул подключений и т. д. остались по умолчанию.
- **Паузы демо-конвейера были выключены.** С ними один worker разбирает примерно одно бронирование за 2,4 секунды, и проверка «нет зависших `pending`» требовала бы минут ожидания, а не секунд.
