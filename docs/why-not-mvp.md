# Почему HotelPulse — не просто MVP

У MVP есть фронтенд, база, очередь, и «всё как-то работает». Этот документ про другое: какие решения отличают HotelPulse от такой версии. Для каждого решения показано, что сломалось бы в боевой эксплуатации без него. Подробности и причины — в [ADR](adr/README.md), незнакомые термины — в [словарике](adr/glossary.md).

Главная мысль проекта: **правила, от которых зависят деньги и данные, обеспечивает то место, которое нельзя обойти**. Это база данных и брокер сообщений, а не «аккуратный код». Поэтому эти правила одинаково работают в двух реализациях на разных языках (.NET и Laravel), и обе проверяются одними и теми же тестами.

## Решения и что они защищают

| Наивная версия делает так… | …и в бою ломается так | HotelPulse делает так | ADR |
|---|---|---|---|
| проверяет «комната свободна?» в коде, потом пишет | два одновременных запроса продают одну комнату дважды | запрет пересечений — ограничение в самой базе | [0001](adr/0001-concurrency-in-sql.md) |
| меняет статус через «прочитал → изменил → сохранил» | отмена и worker затирают друг друга | смена статуса одним `UPDATE … WHERE status = …` | [0001](adr/0001-concurrency-in-sql.md) |
| пишет в базу, потом отдельно отправляет в очередь | сбой между шагами — бронирование навсегда «ожидает» | outbox: письмо в той же транзакции, что и данные | [0002](adr/0002-transactional-outbox-with-publisher-confirms.md) |
| считает письмо отправленным, когда оно ушло в сеть | брокер не принял — письмо потеряно молча | «отправлено» только после подтверждения брокера | [0002](adr/0002-transactional-outbox-with-publisher-confirms.md) |
| записывает поле, посчитанное из старого чтения | шаги worker'а пропадают из таймлайна | новое значение считается внутри `UPDATE` | [0003](adr/0003-timeline-append-in-sql.md) |
| проверяет idempotency-ключ последовательными тестами | повтор запроса получает «даты заняты» вместо своего бронирования | при любом конфликте сначала проверяется ключ | [0004](adr/0004-idempotent-replay-on-exclusion-violation.md) |
| пускает все вставки одновременно | при всплеске — взаимоблокировки и ошибки 500 | вставки в одну комнату встают в очередь | [0005](adr/0005-advisory-lock-per-room.md) |
| подтверждает бронирование, пока пользователь ждёт | медленно, а сбой внешней системы роняет запрос | сразу 202, дальше очередь и worker | [0007](adr/0007-async-booking-with-queue.md) |
| кэширует «как получится» | устаревшие данные, а упавший Redis роняет сайт | база — источник истины, версии ключей, без Redis — `BYPASS` | [0008](adr/0008-cache-is-optional.md) |
| при ошибке worker'а всегда повторяет (или всегда выбрасывает) | очередь забита сломанным сообщением или бронирования теряются | три вида ошибок, у каждого своё правило | [0009](adr/0009-retries-and-poison-messages.md) |
| хранит деньги во float, даты «включительно» | копеечные расхождения, потерянная ночь между гостями | точные числа, `[заезд, выезд)`, UTC | [0010](adr/0010-money-and-dates.md) |
| правит базу руками или правит старые миграции | у каждого окружения своя схема | нумерованные SQL-миграции под замком, одна схема на обе реализации | [0011](adr/0011-schema-as-sql-migrations.md) |
| «работает, пока работает» | хостинг не знает, жив ли процесс; деплой обрывает обработку; логи не связать | readiness и liveness, аккуратная остановка, JSON-логи с номером запроса | [0012](adr/0012-operability.md) |
| пароль в репозитории, отладка включена, root | утечки, трассировки клиенту | секреты из окружения, без ключа не стартуем, не root, CORS по списку | [0013](adr/0013-secure-defaults.md) |
| «у меня работает» | гонки проявляются только в проде | спека → тесты на настоящих сервисах → параллельные тесты ×3 в CI | [0014](adr/0014-quality-gates.md) |

## Ошибки, которые нашли проверки, а не пользователи

Это, пожалуй, лучший аргумент, что подход работает: ниже ошибки, найденные в уже «работающей» системе.

1. **Отмена стирала шаги worker'а** — нашлось при разборе правил конкурентности ([0003](adr/0003-timeline-append-in-sql.md)).
2. **Outbox терял письма, если брокер их не принял** — нашлось там же ([0002](adr/0002-transactional-outbox-with-publisher-confirms.md)).
3. **Повтор запроса с тем же ключом получал 409** — нашёл первый же параллельный тест ([0004](adr/0004-idempotent-replay-on-exclusion-violation.md)).
4. **Взаимоблокировки при параллельных бронированиях** — тоже параллельный тест, примерно в каждом третьем запуске ([0005](adr/0005-advisory-lock-per-room.md)).
5. **CORS молча разрешал все адреса** (Laravel): конфиг читал настройку до её загрузки ([0013](adr/0013-secure-defaults.md)).
6. **Веб-процесс не перезапускался после падения** (Laravel): мешал оставшийся файл состояния Octane ([0012](adr/0012-operability.md)).
7. **Стандартная защита миграций Laravel не защищала** при кэше в памяти процесса ([0011](adr/0011-schema-as-sql-migrations.md)).

## Что сознательно не сделано

Честный список. Каждый пункт — понятный следующий шаг, а не забытая дыра.

| Чего нет | Почему сейчас нет | Как добавить |
|---|---|---|
| Аутентификация | не нужна для демо; любой, кто знает ID, видит бронирование | Laravel Sanctum, политики доступа ([спека](specs/laravel-port.md)) |
| Мультитенантность | одна «компания» | `tenant_id` в таблицах и ограничениях + Row Level Security |
| Метрики | хватает логов и health | OpenTelemetry: время запросов, длина очереди, возраст старейшей строки outbox |
| Сторож зависших бронирований | ADR-0002 и ADR-0009 закрывают известные причины | периодическая задача переопубликует `pending` старше N минут |
| Dead letter queue | проблемное бронирование помечается `rejected` с причиной | отдельная очередь для ручного разбора |
| Часовой пояс отеля | все правила в UTC | отмена «до полуночи по времени отеля» |
| Статический анализ PHP, нагрузочный тест | в этой среде не ставится Larastan; k6 не написан | `composer require --dev larastan/larastan`; сценарий k6 с порогами из спеки |
