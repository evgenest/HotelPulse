# ADR-0001. За целостность при одновременных запросах отвечает база

**Статус:** принято (с версии 1.0.0, перепроверено 2026-11-03)

## Контекст
Два человека в одну секунду бронируют одну и ту же комнату на одни и те же даты. Сервер API может быть запущен в нескольких копиях, поэтому запросы обрабатывают разные процессы.

## Проблема
Самый очевидный код такой:
1. `SELECT`: есть ли бронирования на эти даты?
2. Если нет, `INSERT`.

Оба запроса одновременно делают шаг 1, оба видят «свободно», оба делают шаг 2. Получается двойное бронирование. Это **гонка** [[16]](glossary.md#t16). Замок в коде (`lock` в C#) не поможет: он работает внутри одного процесса, а процессов несколько.

## Решение
Правила записываем **в саму базу**. Её нельзя обойти, и она видит все запросы сразу:
- **Двойное бронирование** запрещает exclusion constraint [[5]](glossary.md#t5): «у одной комнаты нет двух активных бронирований с пересекающимися датами [[7]](glossary.md#t7)». Второй запрос получает ошибку, API отвечает 409 [[27]](glossary.md#t27).
- **Смена статуса** — через compare-and-set [[17]](glossary.md#t17): «поставь *confirmed*, только если сейчас *pending*».
- **Повтор запроса** ловит первичный ключ [[4]](glossary.md#t4) на Idempotency-Key [[24]](glossary.md#t24).

Прочитать данные в коде можно, например чтобы выбрать текст ошибки. Но решение «можно или нельзя» принимает база в момент записи.

## Альтернативы
- **Проверка в коде** — гонка, описана выше.
- **Занять строку заранее** (`FOR UPDATE` [[9]](glossary.md#t9)) — нового бронирования ещё нет, занимать нечего.
- **Строгий режим базы** (SERIALIZABLE [[11]](glossary.md#t11)) — работает, но конфликты случаются чаще, и каждый нужно повторять.
- **Замок в Redis** — Redis у нас только кэш [[26]](glossary.md#t26). Упадёт Redis — пропадёт и защита.

## Последствия
- Защита работает, даже если в базу пишет другой код, например будущая Laravel-версия.
- Ошибки базы нужно превращать в понятные ответы API (таблица кодов — в [[15]](glossary.md#t15)).
- Проверять нужно **параллельными** тестами [[28]](glossary.md#t28).

## Как объяснить на собеседовании
> «Если правило ломается, когда два запроса идут одновременно, проверять его должна база. Только она видит оба запроса. Для пересекающихся дат в Postgres есть специальное ограничение, для смены статуса — UPDATE с условием в WHERE.»

- `apps/HotelPulse.Infrastructure/Postgres/BookingRepository.cs` — `TryCompleteAsync`, `TryCancelAsync` (UPDATE с условием)
