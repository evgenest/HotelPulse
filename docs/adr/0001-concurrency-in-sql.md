# ADR-0001. Конкурентность обеспечивает база, а не код приложения

**Статус:** принято (действует с 1.0.0, перепроверено 2026-11-03)

## Контекст
Одну и ту же комнату могут бронировать одновременно несколько пользователей. API может работать в нескольких экземплярах, worker тоже. Статус бронирования меняют сразу трое: API (создание, отмена), worker (подтверждение или отказ) и обработчик ошибок (`MarkFailedAsync`).

## Проблема
Самый очевидный код — «прочитал → проверил → записал»:

```csharp
var busy = await db.QueryAsync("SELECT ... WHERE room = @r AND dates overlap");
if (busy.Any()) return Conflict();
await db.ExecuteAsync("INSERT INTO bookings ...");
```

Между SELECT и INSERT проходит время, и второй запрос успевает выполнить свой SELECT. Оба видят «свободно», и оба вставляют. Это гонка класса **TOCTOU** (time-of-check to time-of-use). Блокировка в C# (`lock`, `SemaphoreSlim`) её не исправит: она работает только внутри одного процесса, а экземпляров API несколько.

## Решение
Каждый инвариант проверяет то место, которое видит все одновременные транзакции, — Postgres:

1. **Нет пересекающихся проживаний** — exclusion constraint `bookings_no_overlapping_stay` (GiST по `hotel_id`, `room_id`, `daterange(check_in, check_out, '[)')`), только для статусов `pending` и `confirmed`. Вторая вставка получает ошибку `23P01`, API отвечает 409.
2. **Смена статуса** — compare-and-set: `UPDATE ... WHERE id = @id AND status = 'pending'`. Если строку уже изменили, обновится 0 строк, и код это видит.
3. **Идемпотентность** — первичный ключ `idempotency_keys.idempotency_key`.
4. **Outbox relay в нескольких экземплярах** — `SELECT ... FOR UPDATE SKIP LOCKED`.

Читать строку в коде можно, например чтобы выбрать текст ошибки (так делает отмена). Важно, чтобы в WHERE при записи стояли те же условия.

## Рассмотренные альтернативы
- **Проверка в коде** — гонка, описана выше.
- **`SELECT ... FOR UPDATE` с последующей проверкой** (пессимистичная блокировка) — работает, но блокировать нечего: строки нового бронирования ещё нет. Пришлось бы блокировать комнату, а это и есть ADR-0005. Сам по себе такой вариант не гарантирует запрет пересечений, если кто-то вставит запись в обход этого кода.
- **Уровень изоляции SERIALIZABLE** — корректно, но любой конфликт превращается в `40001`, и код должен уметь повторять транзакции. Запросы конфликтуют чаще, чем нужно.
- **Распределённый lock в Redis** — Redis у нас только кэш (см. `CLAUDE.md`). Если Redis упадёт или ключ истечёт по TTL, гарантия пропадёт.

## Последствия
- Гарантия держится, даже если в базу пишет другой код. Это важно для Laravel-порта: обе реализации пишут в одну и ту же схему.
- Код должен правильно переводить ошибки Postgres в HTTP-коды: `23P01` → 409, `23505` на idempotency key → повтор.
- Тестировать нужно **настоящей параллельностью** (`ConcurrencyTests`). Последовательные тесты гонку не ловят.

## Как объяснить на собеседовании
«Инвариант, который нарушают параллельные запросы, должен проверять тот, кто видит все запросы. Это база данных. В коде я читаю данные, чтобы выбрать ответ пользователю, а гарантию даёт constraint или условный UPDATE. Для пересечения диапазонов дат в Postgres есть exclusion constraint, обычный UNIQUE так не умеет.»
