# ADR-0005. Advisory lock на комнату против взаимоблокировок

**Статус:** принято 2026-11-03 (коммит `5db75e7`).

## Контекст
Пересечения запрещает exclusion constraint (ADR-0001). Десять одновременных запросов на одну комнату и одни даты должны дать один 202 и девять 409.

## Проблема (найдена новым параллельным тестом, проявлялась примерно в каждом третьем прогоне)
Часть запросов получала **500 `40P01: deadlock detected`**. Так устроены exclusion constraints: каждая вставка сначала добавляет запись в GiST-индекс, а потом проверяет конфликты и **ждёт** завершения конкурирующих незакоммиченных транзакций. Транзакция A ждёт B, а B ждёт A — получается взаимоблокировка. Postgres её обнаруживает и обрывает одну из транзакций. Чем больше одновременных конфликтующих вставок, тем больше таких циклов.

Первая попытка — повторять транзакцию при `40P01` (до трёх раз, с паузой). Помогло не всегда: повторы снова попадали в тот же «шторм».

## Решение
В начале транзакции создания:

```sql
SELECT pg_advisory_xact_lock(hashtextextended(@roomKey, 0)) -- roomKey = "hotel/room"
```

Вставки **в одну комнату** выстраиваются в очередь. Блокировка снимается сама при commit или rollback (`xact`). Вставки в разные комнаты по-прежнему идут параллельно. Constraint остаётся гарантией. Lock убирает только взаимоблокировки: даже если кто-то вставит запись без него, двойного бронирования не будет. Повтор при `40P01` оставлен как страховка.

8 прогонов подряд — все зелёные.

## Рассмотренные альтернативы
- **Только повторы** — недостаточно (см. выше), и запросы впустую нагружают базу.
- **`SELECT ... FROM rooms WHERE ... FOR UPDATE`** — тоже очередь на комнату через блокировку строки. Работает так же. Advisory lock не трогает строки, его видно по назначению, и он не мешает чтению каталога.
- **SERIALIZABLE** — вместо взаимоблокировок будут `40001`, повторы всё равно нужны.

## Последствия
- Бронирования **одной комнаты** обрабатываются строго по очереди. Для отеля это нормально: каждое ожидание — миллисекунды.
- Коллизия хэшей (две разные комнаты с одним 64-битным хэшем) приведёт лишь к лишнему ожиданию, а не к ошибке.

## Как объяснить на собеседовании
«Exclusion constraint гарантирует корректность, но при сильной конкуренции даёт взаимоблокировки. Я ставлю транзакционный advisory lock на ресурс, который вызывает конфликт: здесь это комната. Так вставки выстраиваются в очередь. Корректность по-прежнему обеспечивает constraint, lock нужен только для того, чтобы запросы не мешали друг другу.»
