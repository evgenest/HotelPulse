# Словарик

Термины из ADR простыми словами. В тексте решений стоят сноски вида [[5]](#t5) — номер ведёт сюда. Примеры на SQL используют только SELECT, INSERT, UPDATE и WHERE.

---

## База данных и SQL

<a id="t1"></a>
### 1. Транзакция
Пачка запросов, которая выполняется **по принципу «всё или ничего»**. Пример: «вставить бронирование» и «вставить сообщение для очереди». Либо выполнятся оба, либо ни один. Начинается с `BEGIN`, заканчивается `COMMIT` или `ROLLBACK` (см. [[2]](#t2)).

<a id="t2"></a>
### 2. COMMIT и ROLLBACK
- `COMMIT` — «сохранить всё, что сделали в транзакции». Только после этого изменения видят другие.
- `ROLLBACK` — «отменить всё», как будто ничего и не было.

<a id="t3"></a>
### 3. Constraint (ограничение)
Правило, записанное **в самой таблице**. База сама не даст его нарушить, кто бы ни писал данные. Примеры: `NOT NULL` — поле не может быть пустым, `CHECK (total >= 0)` — сумма не может быть отрицательной. Если запрос нарушает правило, база возвращает ошибку и ничего не записывает.

<a id="t4"></a>
### 4. Первичный ключ и UNIQUE
- **UNIQUE** — ограничение «значение в этой колонке не может повторяться».
- **Первичный ключ (PRIMARY KEY)** — главный уникальный идентификатор строки, например `id`. Это тоже UNIQUE.

Вторая вставка того же значения получает ошибку `23505` (см. [[15]](#t15)).

<a id="t5"></a>
### 5. Exclusion constraint (ограничение-исключение)
Расширенная версия UNIQUE. UNIQUE умеет проверять только «два значения **равны**». Exclusion constraint умеет проверять «две строки **конфликтуют**», например «даты проживания **пересекаются**». У нас правило такое: «для одной и той же комнаты не может быть двух активных бронирований с пересекающимися датами». Нарушение даёт ошибку `23P01` ([[15]](#t15)). Есть в PostgreSQL, в MySQL такого нет.

<a id="t6"></a>
### 6. Индекс и GiST
- **Индекс** — оглавление для таблицы. По нему база быстро находит нужные строки и не перебирает всю таблицу.
- **GiST** — особый вид индекса, который умеет искать «пересечения» (дат, областей на карте и т. п.). Exclusion constraint ([[5]](#t5)) работает поверх такого индекса.

<a id="t7"></a>
### 7. daterange и `[)`
`daterange(check_in, check_out, '[)')` — «диапазон дат» в PostgreSQL. `[)` означает: дата заезда **входит** в диапазон, дата выезда **не входит**. Поэтому гость, который выезжает 5-го, не мешает гостю, который заезжает 5-го.

<a id="t8"></a>
### 8. RETURNING
Добавка к `UPDATE` или `INSERT`: «после изменения сразу верни мне изменённую строку». Без неё понадобился бы ещё один `SELECT`.

<a id="t9"></a>
### 9. Блокировка строк: FOR UPDATE и SKIP LOCKED
- `SELECT ... FOR UPDATE` — «прочитай строки и **займи** их до конца моей транзакции». Другие, кто захочет их изменить, будут ждать.
- `SKIP LOCKED` — «строки, которые уже кто-то занял, **пропусти**, не жди». Так несколько копий relay ([[22]](#t22)) разбирают outbox, не мешая друг другу и не публикуя одно и то же дважды.

<a id="t10"></a>
### 10. Advisory lock (`pg_advisory_xact_lock`)
«Замок по договорённости». Он не привязан к строке. Это просто **число**, которое транзакция может занять. Пока она его держит, другая транзакция, которая хочет то же число, ждёт.
- `pg_advisory_xact_lock(число)` — занять замок до конца транзакции. Он сам освобождается на COMMIT или ROLLBACK, забыть его снять нельзя.
- `hashtextextended('hotel/room', 0)` — превращает текст в число (хэш, [[34]](#t34)). Так у каждой комнаты получается свой номер замка.

<a id="t11"></a>
### 11. Уровень изоляции и SERIALIZABLE
Насколько транзакции «видят» друг друга, пока работают. По умолчанию в PostgreSQL каждый запрос видит то, что уже закоммичено ([[2]](#t2)). `SERIALIZABLE` — самый строгий уровень: база гарантирует результат, как будто транзакции шли строго по очереди. Если не получается, одна транзакция получает ошибку `40001`, и её нужно повторить.

<a id="t12"></a>
### 12. jsonb и функции для него
`jsonb` — колонка, в которой хранится JSON (у нас список событий таймлайна).
- `a || b` — склеить два JSON-массива: `[1,2] || [3]` = `[1,2,3]`.
- `jsonb_array_elements(массив)` — разложить массив на отдельные строки, по одной на элемент, чтобы с каждым что-то сделать.
- `WITH ORDINALITY` — к каждому элементу добавить его порядковый номер (1, 2, 3…), чтобы потом собрать в том же порядке.
- `jsonb_agg(...)` — обратная операция: собрать строки обратно в один массив.
- `e || '{"current": false}'` — в объекте `e` поставить поле `current` в `false`.
- `coalesce(x, y)` — «если x пустой (NULL), возьми y». Защита на случай пустого массива.

<a id="t13"></a>
### 13. Миграция
SQL-файл, который меняет структуру базы (добавить таблицу, колонку, ограничение). Миграции пронумерованы (`001_init.sql`, `002_...`) и применяются по порядку. Уже применённую миграцию не правят, вместо этого пишут новую.

<a id="t14"></a>
### 14. Хранимое значение против прочитанной копии
Когда код сделал `SELECT`, у него в памяти **копия** строки. Пока он думает, настоящая строка в базе может измениться. Если потом записать что-то, посчитанное из старой копии, свежие изменения затрутся (см. [[18]](#t18)).

<a id="t15"></a>
### 15. Коды ошибок PostgreSQL (SQLSTATE)
У каждой ошибки есть пятизначный код. Наши:
| Код | Что значит | Что отвечает API |
|---|---|---|
| `23505` | нарушен UNIQUE или первичный ключ ([[4]](#t4)) | для Idempotency-Key — повтор ([[24]](#t24)) |
| `23P01` | нарушен exclusion constraint ([[5]](#t5)) — даты заняты | 409 |
| `40P01` | deadlock ([[19]](#t19)) — база оборвала транзакцию | повторить |
| `40001` | конфликт при SERIALIZABLE ([[11]](#t11)) | повторить |

## Конкурентность (когда много запросов одновременно)

<a id="t16"></a>
### 16. Гонка (race condition) и TOCTOU
Ошибка, которая появляется, только когда два запроса выполняются **одновременно**. **TOCTOU** (time of check → time of use, «проверил в одно время — использовал в другое») — частый вид гонки. Код проверил «комната свободна», но, пока он дошёл до записи, другой запрос её уже занял.

<a id="t17"></a>
### 17. Compare-and-set (CAS)
«Измени, **только если** значение всё ещё такое, как я думаю»:
```sql
UPDATE bookings SET status = 'confirmed' WHERE id = 'b1' AND status = 'pending';
```
Если кто-то уже поменял статус, `WHERE` не совпадёт и обновится 0 строк. Код видит «0» и понимает: «меня опередили». Проверка и запись происходят **одним** запросом, поэтому гонки нет.

<a id="t18"></a>
### 18. Lost update (потерянное обновление)
Два участника прочитали одну строку, каждый поменял свою копию ([[14]](#t14)) и записал. Побеждает тот, кто записал последним, а изменения первого **молча пропадают**.

<a id="t19"></a>
### 19. Deadlock (взаимоблокировка)
A ждёт B, а B ждёт A. Никто не может продолжить. PostgreSQL замечает такие ситуации и обрывает одну из транзакций с ошибкой `40P01` ([[15]](#t15)). Её работа отменяется, и её можно повторить.

<a id="t20"></a>
### 20. Оптимистичная и пессимистичная блокировка
- **Пессимистичная:** «сначала займу, потом работаю» (`FOR UPDATE` [[9]](#t9), advisory lock [[10]](#t10)). Другие ждут.
- **Оптимистичная:** «работаю без замка, а при записи проверяю, что никто не вмешался» (CAS [[17]](#t17), колонка `version`). Если вмешались, повторяю.

## Очереди и сообщения

<a id="t21"></a>
### 21. Брокер сообщений, RabbitMQ, очередь
**Брокер** — «почта» между программами. API кладёт письмо («обработай бронирование b1») и сразу отвечает пользователю. Worker ([[25]](#t25)) забирает письма и обрабатывает. **RabbitMQ** — конкретный брокер. **Очередь** — ящик, где письма ждут. **Exchange** — сортировщик, который решает, в какую очередь положить письмо.

<a id="t22"></a>
### 22. Dual write, transactional outbox, relay
- **Dual write** — запись в два разных места (база + брокер) по очереди. Если упасть между ними, данные разойдутся.
- **Transactional outbox** («исходящие в той же транзакции») — письмо сначала кладём **в таблицу `outbox` в той же базе и той же транзакции** ([[1]](#t1)), что и бронирование. Либо есть и бронирование, и письмо, либо нет ничего.
- **Relay** — отдельный цикл, который берёт письма из `outbox`, отправляет их в брокер и помечает отправленными.

<a id="t23"></a>
### 23. ack, nack, publisher confirms, mandatory
- **ack / nack** — «принял» или «не принял». Worker отвечает брокеру ack, когда обработал письмо, и nack, когда не смог (тогда письмо вернётся).
- **Publisher confirms** — то же самое в обратную сторону: **брокер** отвечает отправителю «письмо у меня, сохранено». Без этого отправитель знает только, что письмо ушло в сеть.
- **mandatory** — флаг «если письмо некуда положить (нет подходящей очереди), верни ошибку, а не выбрасывай молча».

<a id="t24"></a>
### 24. At-least-once, идемпотентность, Idempotency-Key
- **At-least-once** («хотя бы один раз») — письмо точно дойдёт, но может дойти **дважды**.
- **Идемпотентность** — повторить действие сколько угодно раз безопасно, результат тот же. Пример: worker получил письмо про бронирование, которое уже подтверждено, и просто его игнорирует.
- **Idempotency-Key** — заголовок HTTP-запроса с уникальной строкой от клиента. Если клиент повторит запрос с тем же ключом (сеть моргнула, кнопку нажали дважды), сервер вернёт **тот же** результат и не создаст второе бронирование.

<a id="t25"></a>
### 25. Worker и consumer
Фоновая программа, которая не отвечает на HTTP, а **читает очередь** ([[21]](#t21)) и выполняет работу: подтверждает или отклоняет бронирования. Consumer — «потребитель сообщений», в нашем случае то же самое.

## Прочее

<a id="t26"></a>
### 26. Кэш, Redis, инвалидация
**Кэш** — быстрая копия данных, чтобы не ходить каждый раз в базу. **Redis** — быстрое хранилище в памяти, у нас это кэш. **Инвалидация** — удалить устаревшую копию после изменения данных, чтобы следующий запрос взял свежие данные из базы.

<a id="t27"></a>
### 27. HTTP-коды
`200` — готово. `202` — принято, обработка идёт в фоне. `404` — не найдено. `409` — конфликт (даты заняты, бронирование уже нельзя отменить). `500` — ошибка сервера: у нас её быть не должно.

<a id="t28"></a>
### 28. Интеграционный и параллельный тест
- **Интеграционный тест** — запускает настоящие Postgres, Redis и RabbitMQ (в Docker) и проверяет систему целиком.
- **Параллельный тест** — отправляет много запросов **одновременно**. Только так ловятся гонки ([[16]](#t16)). Обычные тесты шлют запросы по очереди и гонок не видят.

<a id="t29"></a>
### 29. Монорепо
Один git-репозиторий, в котором лежат несколько приложений (у нас .NET API, Laravel API, фронтенд).

<a id="t30"></a>
### 30. Docker и supervisord
- **Docker** — упаковывает приложение со всем нужным в «контейнер», который одинаково запускается где угодно.
- **supervisord** — программа внутри контейнера, которая запускает несколько процессов (веб-сервер, worker, relay) и перезапускает их, если они упали.

<a id="t31"></a>
### 31. CDC (Change Data Capture), Debezium
Способ узнавать об изменениях в базе, читая её внутренний журнал изменений. **Debezium** — популярный инструмент для этого. Альтернатива relay с опросом таблицы, но требует отдельной инфраструктуры.

<a id="t32"></a>
### 32. Round-trip
Один «сходил и вернулся» по сети: запрос туда, ответ обратно. Каждый round-trip — это лишние миллисекунды.

<a id="t33"></a>
### 33. Partial index (частичный индекс)
Индекс ([[6]](#t6)) не по всей таблице, а только по строкам, которые подходят под условие. Например, только активные бронирования: `WHERE status IN ('pending','confirmed')`.

<a id="t34"></a>
### 34. Хэш
Функция, которая превращает любой текст в число фиксированного размера. Одинаковый текст всегда даёт одно и то же число. Разные тексты почти всегда дают разные числа, но очень редко могут совпасть (коллизия).
