# ADR-0003. Отмена дописывает событие к актуальной версии, а не к старой копии

**Статус:** принято 2026-11-03.

## Контекст
У бронирования есть таймлайн для экрана: «получено → отправлено → доставлено worker'у → комната заблокирована → итог». Его хранят в колонке JSON [[12]](glossary.md#t12). Worker по ходу работы дописывает туда шаги. Отмена добавляет в конец «бронирование отменено».

## Проблема: потерянное обновление
1. API при отмене прочитал таймлайн: `[получено, отправлено]`. Это **копия** [[14]](glossary.md#t14).
2. В это время worker дописал `доставлено` (бронирование всё ещё «ожидает»).
3. API записал `[получено, отправлено, отменено]` — свою старую копию плюс отмену.

Шаг «доставлено» исчез. Это **lost update** [[18]](glossary.md#t18). Проверка статуса [[17]](glossary.md#t17) прошла, потому что статус не менялся: менялся таймлайн.

## Решение
API больше не отправляет весь таймлайн, только **одно новое событие**. База сама берёт **то, что лежит в строке сейчас**, и дописывает его в конец. Всё делается одним UPDATE, поэтому вклиниться между чтением и записью некому.

## Альтернативы
- **Номер версии строки** (оптимистичная блокировка [[20]](glossary.md#t20)) — при несовпадении версии повторять. Универсально, но нужна миграция [[13]](glossary.md#t13) и логика повторов.
- **Занять строку заранее** (`FOR UPDATE` [[9]](glossary.md#t9)) — работает, но держит замок дольше, чем нужно.
- **Отдельная таблица событий**, по строке на событие — самый правильный вариант на будущее. Конфликтов нет вообще, но для демо пока лишнее.

## Последствия
- Отмена больше не стирает шаги worker'а. Это проверяет отдельный тест.
- Правило «как дописать событие» теперь есть и в C#, и в SQL. При изменении нужно править оба места.

## Как объяснить на собеседовании
> «Проверка в WHERE защищает только те колонки, которые проверяешь. Если пишешь другую колонку, посчитанную из старого чтения, затрёшь чужие изменения. Решение — пусть база сама посчитает новое значение из текущего: "допиши в конец", а не "вот тебе весь список".»
